## Метод и ограничение runner

Попытка запуска:

```bash
claude plugin eval plugins/cdd-tasks --case post-merge-sync --runs 3 \
  --max-cost-usd 4 --no-publish --no-scaffold --trust-plugin \
  --output-dir plugins/cdd-tasks/evals/results/lifecycle-red
```

CLI завершился с кодом 2 до ответа модели: OAuth session expired, refresh failed.
Этот сбой не считается RED. Авторизация не менялась. Использован предусмотренный
планом fallback: свежие агенты текущего Codex, по три независимых прогона каждого
case без руководства, со старым и с новым руководством. Для пар merge/track и
multi/sprint три агента каждого варианта отвечали на оба case отдельно.

Разрешено чтение только prompt и соответствующих руководств, без сети, graders
и реальных мутаций. Единственная запись — собственный файл ответа. Полные ответы
сохранены локально в игнорируемом `plugins/cdd-tasks/evals/results/`:
`{life,merge,track,multi,sprint}-{control,old,new}-{1,2,3}.md`.
Итого 45 ответов-case. Решения и команды прочитаны автором целиком и вручную
сопоставлены с criteria.md; автоматические scores не использовались.

Это не сопоставимый benchmark Claude. Grader `tool_used: Skill` и фактическое
обнаружение плагина этим fallback не проверены. Read-only сценарий доказывает
качество предложенного маршрута, а не исполнение реального merge/recovery/записи.

Baseline lifecycle и регрессий — исходник `ef68144`; merge/track baseline —
`07080f7` (Task 1 уже завершена). Новые lifecycle ответы проверяют Task 1 (`07080f7`),
merge/track и регрессии — Task 2 (`2ac4891`). Task 3 не меняет эти руководства.

Наблюдаемые различия:

- Старые lifecycle ответы трактовали открытую frontend issue после merge как
  расхождение и не знали recovery: «Конкретная команда recovery release issues
  в документах отсутствует» (life-old-1). Новые 3/3 различают Ready for build,
  Ready for release, Health check и production success, дают reconcile-issues
  с исходным ID, проверяют результат и сохраняют rollback/reopen.
- Старые track ответы не знали модель: «Документы не определяют, назначать ли
  поле только родителю или каждому текущему ребёнку, и наследует ли исторический
  ребёнок новый трек» (track-old-2). Новые 3/3 используют явные записи текущих детей
  при смешанной истории, сохраняют чужие поля, ждут разрешённого merge/CI при
  отсутствии option и различают запись поля и публикацию графа.
- Merge baseline уже 3/3 уважал прямое разрешение владельца вопреки старому скиллу.
  Это регрессия и устранение противоречия текста, не доказанное улучшение поведения.
  Контроль без руководства сохранял границы разрешения, но не знал frontend lifecycle.
- Старый multi-repo grader говорил, что оба PR закрывают задачи. По плану уточнён
  только пункт 5: frontend Closes задаёт связь, CD закрывает; infra merge закрывает.
  По прежним критериям baseline проходил 3/3, но не описывал актуальное закрытие
  frontend: «затем frontend PR, закрывающий родителя» (multi-old-2).
- Next-sprint сохраняет прежние гарантии: выбор по датам, Sprint 9, только поле
  Sprint, проверка Status после записи; пробел в расписании не угадывается.
  Без руководства неизвестны командные фильтры представлений.

## Принятые решения и доставка

- OAuth-сбой заменён разрешённым fallback. Ограничение: проверено поведение
  доступной модели, а не Claude runner и его обнаружение Skill.
- Успешный старый merge-authorization baseline не назван RED. Ограничение:
  по этим прогонам нельзя приписывать правке улучшение решения о merge.

Этап заканчивается PR. Merge и обновление установленного плагина ждут отдельного
поручения. После merge: штатный `codex plugin marketplace upgrade cdd --json`,
сравнение установленного руководства с источником и проверка discovery; уже
загруженная сессия не получает новый текст автоматически. Кэш вручную не правился.
