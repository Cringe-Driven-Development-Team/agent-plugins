# apidog-cdd: контекст проекта и ревью контрактов

> Исторический документ: исходное имя `apidog-cdd` заменено на `cdd-apidog`
> по [согласованной спецификации](2026-11-04-cdd-apidog-rename-design.md).
> Прежние команды и результаты ниже сохранены как запись первоначальной работы.

Статус: согласована пользователем. Дата: 2026-11-04.

## Зачем

Агенту нужен контекст Apidog команды CDD без повторного поиска ссылок и без
копирования официальных инструкций. Пользователь выбрал один `apidog-cdd`;
отдельный универсальный `apidog-ops` сейчас не создаём.

## Рассмотренные подходы

1. Только восемь официальных скиллов: покрывают CLI, ветки, импорт/экспорт,
   тестирование и API lifecycle, но не знают проект CDD и не описывают полное ревью MR.
2. **Выбран:** один `apidog-cdd` поверх официальных скиллов; проектный контекст
   и небольшой справочник по ревью и выбору инструментов.
3. `apidog-ops` плюс `apidog-cdd`: позволяет переиспользовать общую методику,
   но пока создаёт лишнюю поддерживаемую сущность. Вернуться при реальной
   потребности вне CDD.

## Поставка и структура

Предложение автора: плагин `apidog-cdd@cdd` в
`Cringe-Driven-Development-Team/agent-plugins`, доступный Claude Code и Codex.
Следовать актуальной структуре соседних собственных плагинов и обоих каталогов.

- `SKILL.md`: точный триггер для Apidog/контрактов CDD, карта проекта,
  источники правил и маршрутизация на установленные официальные скиллы.
- `references/review.md`: ревью MR и ограничения CLI/MCP.
- Два манифеста, записи двух marketplace, каталог README и необходимые
  изменения существующих проверок упаковки.

Не включать копии восьми официальных скиллов, новый MCP, обёртку над CLI,
автоматический вход, секреты или снимок всех эндпоинтов. Не загружать весь
официальный набор: выбирать скиллы по задаче. Если нужный скилл не установлен,
сообщить об этом и дать проверенную команду установки; доступные операции
читать через текущий `--help`, не блокировать их искусственно.

## Работа с проектом и правами

Включить просмотр проекта, команды, настроек, участников и прав в пределах
фактически доступных инструментов. Проверено на CLI 2.2.12:

- `project get` возвращает teamId, модули и ветки; `project settings get` — настройки.
- `team get` возвращает `roleType`, `roleName`, `roleBuiltIn`, `teamPermissions`
  текущего аккаунта. Это не список персональных прав всех участников проекта.
- В проверенных командах и ответах нет полного списка участников.
  Подключённый MCP предлагает только чтение/обновление OpenAPI и чтение refs.

При запросе участников сначала сверить актуальные capabilities. Если данных нет,
явно указать границу и использовать доступный разрешённый веб-интерфейс либо
документированный API; не придумывать ручки и не выдавать собственную роль за
полный аудит доступа. Реализация скилла не требует разработки обхода ограничений.
Изменение состава/прав не входит в начальный объём.

Ответ настроек содержит, в частности, токен Cloud Mock: выводить только нужные
поля, не печатать весь ответ и не включать секреты в артефакты ревью.

## Ревью MR

1. По URL определить проект, MR и целевую ветку; получить актуальные данные MR,
   исходную ветку и выбранные ресурсы. Не подменять scope MR diff всех веток.
2. CLI `merge-request preview` — кандидаты на уровне ресурсов, не авторитетный
   backend diff и не diff полей. Проверять partial/unsupportedContentFields;
   отсутствие поддерживаемых данных не означает отсутствие изменений.
3. Для выбранных ресурсов прочитать обе стороны и связанные схемы, сравнить
   тела запросов/ответов, ошибки, auth, required/nullability, примеры и семантику.
   Экспорт OpenAPI не доказывает покрытие mock expectations и других native-ресурсов:
   их читать соответствующими командами либо отметить непроверенными.
4. Сверить с актуальной задачей и потребителями frontend/BFF/backend по необходимости.
   Проверить, не откатываются ли изменения текущей целевой ветки. Использовать
   правила слияния из актуальной документации команды.
5. Для OpenAPI проверять refs, схемы и релевантные примеры. Чтение контракта,
   запуск mock-проверок и проверка реализации — разные уровни доказательств.
6. В замечании: серьёзность, точный ресурс/поле, сценарий проблемы и предлагаемое
   исправление. Указать источники, ветки, время получения и ограничения покрытия.
7. Ревью само по себе не разрешает approve, merge, правки или сообщения.
   Явное поручение пользователя на эти действия не запрашивать повторно;
   перед записью учитывать актуальные ограничения доступа и проверять результат.

MCP удобен для чтения актуального контракта после refresh при подтверждённой
привязке к нужному проекту/ветке. Не считать его снимок доказательством состояния
исходной ветки MR. CLI используется там, где нужны MR, ветки и native-ресурсы.

## Проверка результата

- Валидность скилла, ссылок между его файлами и упаковки обоих hosts.
- Сценарии: чтение main; ревью частичного MR; генерация из sprint-ветки;
  запрос участников при отсутствии списка; настройки с секретными полями.
- Агент не путает кандидатов preview с составом MR, не выдаёт неполные права
  за полные и не публикует результат без поручения.
- Внешние проверки только read-only; правки контрактов и доступов для приёмки
  не требуются. Новые скрипты и тесты на точное совпадение формулировок не нужны.

## Решения, оставленные исполнителю

Точное расположение файлов по текущему стилю репозитория, краткие формулировки,
актуальные CLI аргументы и минимальные изменения существующих packaging-тестов.
Эта спецификация не является разрешением начать реализацию до её согласования.
