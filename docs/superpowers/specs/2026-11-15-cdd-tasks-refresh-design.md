# Актуализация cdd-tasks

## Цель

Скилл ведёт задачи и PR по актуальному процессу команды: правильно различает
merge, сборку, выпуск, production и закрытие задачи; выполняет согласованную
привязку трека без повторного запроса разрешения.

## Проверенные факты

- На `agent-plugins/main` (`7274bdb`) SKILL.md и REFERENCE.md совпадают с
  установленной копией. Устарел исходник, а не только локальный кэш.
- `.github/CONTRIBUTING.md` разделяет frontend и остальные репозитории:
  frontend после merge остаётся открытым в Ready for build, после выпуска —
  Ready for release, после успешного CD — completed/Done.
- В frontend `cd.yml` обновляет release issues после Health check и сохранения
  production success. `reconcile-issues.yml` принимает deployment_id и запускает
  восстановление статусов без повторной выкатки.
- SKILL.md, REFERENCE.md и README плагина содержат устаревшие утверждения
  о закрытии после merge и безусловный запрет bypass.
- Существуют структурный тест и evals multi-repo-task, next-sprint, post-merge-sync.
  Последний требует обновления под текущий процесс frontend.
- Граф docs получает прогресс из поля «Трек» GitHub Projects; одного `issues`
  во frontmatter недостаточно. Новые варианты поля добавляет CI docs на main.

## Выбранный подход

Точечно обновить существующие SKILL.md, REFERENCE.md, README и сценарные проверки.
Этот объём согласован пользователем. Разделение на новые скиллы увеличило бы
число источников правил; обновление только локального кэша не исправило бы
исходник и установку других участников.

## Поведение после изменения

1. **Жизненный цикл.** Отдельно описать frontend и backend/остальные репозитории.
   `Closes` сохраняет связь PR с задачей; frontend не объявляется закрытым или
   выкаченным только по merge. Учесть ручное закрытие/reopen и состояние rollback
   по актуальным правилам, не переопределяя их собственной автоматикой.
2. **Проверка результата.** Отчёт различает merge, CI, course-sync, опубликованный
   Release, production и состояние issue. Проверять только этапы запрошенного
   действия. Ошибка синхронизации и ошибка обновления доски исправляются своими
   recovery-процедурами, без повторной выкатки ради статуса.
3. **Разрешение владельца.** Явное поручение на merge и действующие пользовательские
   инструкции имеют приоритет над ограничениями скилла. При разрешённом bypass
   проверить актуальный head, обязательный CI и конфликты. Не менять rulesets
   и не обходить проваленные проверки. Без такого разрешения действуют правила
   команды; само наличие технического доступа не разрешает merge.
4. **Граф и доска.** Просьба «добавь этот трек в граф» разрешает связанную правку
   docs через docs-modules и привязку указанных задач полем «Трек». До записи
   прочитать текущие значения, иерархию и спринты; учитывать наследование у
   sub-issues. Сохранять статусы, спринты, назначения и посторонние поля.
   Конфликт с существующим другим треком требует отдельного разбора.
   Не приписывать к новому модулю завершённые работы прошлых модулей.
   Если варианта поля ещё нет, подготовить изменение docs и дождаться добавления
   варианта штатным CI после разрешённого merge. Не запускать локальный board sync.
   После записи проверить GitHub и свежий снимок/граф; не объявлять публикацию
   завершённой до наблюдаемого результата. Разрешение на привязку не разрешает merge.
5. **Источники.** Общекомандные правила брать из CONTRIBUTING и workflow владельца;
   пользовательские исключения сохранять как исключения, не выдавая их за
   общекомандную политику. Чтение удалённого документа не отменяет инструкции пользователя.

## Проверки

Перед правкой выполнить безопасные сценарии со старым скиллом, сохранить ошибки
поведения. После правки повторить те же сценарии с новым скиллом:
frontend merge без CD; успешный CD со сбоем обновления задач; backend sync failure;
разрешённый владельцем bypass; добавление трека, отсутствие варианта поля и конфликт
с существующей привязкой. Проверить сохранение чужих полей и отсутствие лишних запросов.

Использовать существующий формат evals и graders. Сценарии не выполняют мутации
реального GitHub, merge или deploy. Структурные проверки и проверки манифестов
дополняют проверку поведения, не заменяя её. Дополнительные правки по результатам
сценариев ограничиваются найденными проблемами.

## Выпуск и границы

Править исходники в agent-plugins; подготовить проверенный PR. Merge — отдельное
поручение. После попадания изменений в источник обновить установленный плагин
штатным механизмом, проверить содержимое SKILL.md/REFERENCE.md и сообщить,
нужна ли новая сессия. Кэш вручную не редактировать.

Не менять реальные задачи, поле «Трек», CI/CD, правила GitHub, приложение или граф
модуля №3 в рамках этой доработки скилла. Не создавать новую систему автоматизации.
