# Следующий спринт в cdd-tasks

Пользователь согласовал четыре пункта: описать представление следующего спринта,
назначать его через поле Sprint с сохранением статуса, проверять результат через
API и определять текущую итерацию с учётом её длительности.

## Подход

Достаточно дополнить существующие SKILL.md и REFERENCE.md. Отдельный проект,
статус или скрипт назначения не нужны: поле Sprint и gh project item-edit уже есть.
Пользователь выбрал эту небольшую правку инструкции.

## Поведение

- `next-sprint` / `Next Sprint` — представление проекта Scrumban №1 с фильтром
  `sprint:@next`; фактическое название сейчас `Next Sprint`, номер представления 8.
- Просьба поставить задачу на следующий спринт разрешает изменить только поле
  Sprint. Статус сохраняется, если пользователь отдельно не поручил его изменить.
- Текущая итерация содержит сегодняшнюю дату: `startDate <= today < startDate +
  duration дней`. Следующая — ближайшая по дате начала после текущей, а не первый
  элемент ответа API. ID итераций каждый раз читаются из проекта.
- Если текущую или следующую итерацию определить нельзя, назначение не выполняется:
  агент сообщает, чего не хватает, и уточняет целевой спринт.
- До изменения читается статус карточки; после — через API повторно читаются Sprint
  и Status. Успех означает нужный iterationId и сохранённый статус.
- Краткое правило находится в SKILL.md; фильтры, выбор итерации и пример проверки —
  в REFERENCE §3. Там же фиксируются действующие фильтры Backlog и Sprint.

## Границы и проверка

Не меняем GitHub, расписание итераций, автоматику и правила создания задач;
не переносим задачи самостоятельно. Установленный кэш плагина вручную не правим.
Контракты PR и правила review остаются вне этой задачи.

Проверка: сценарий без записи в GitHub до и после правки, включая смену спринта,
несортированный ответ API, перерыв и отсутствие следующей итерации; существующие
проверки документов и манифестов, quick_validate. Без проверки на живой карточке.
