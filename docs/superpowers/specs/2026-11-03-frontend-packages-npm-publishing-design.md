# Подключение пакетов frontend-packages к npm Trusted Publishing

## Цель и согласованные границы

Добавить в `Cringe-Driven-Development-Team/agent-plugins` собственный плагин
`frontend-packages` со скиллом `npm-publishing`. Команда «подключи пакет X к
автопубликации» поручает агенту провести существующий пакет репозитория
`Cringe-Driven-Development-Team/frontend-packages` от ручного bootstrap до
проверенной автоматической публикации. Всё доступное автоматизации выполняет
агент; человек подтверждает npm 2FA. Разработка исходников нового пакета в задачу
не входит.

## Рассмотренные подходы

1. **Инструкции и справочник, выбран пользователем.** Использовать существующие
   npm/GitHub CLI или подключённые инструменты и скрипты frontend-packages.
   Минимум собственного кода, агент адаптирует команды к фактическому состоянию.
2. **Скилл и управляющий скрипт.** Скрипт хранит состояние и управляет переходами,
   но требует отдельной поддержки 2FA и восстановления, повторяет часть
   существующего механизма публикации. Не выбран.

Работа небольшая: один скилл, справочник, регистрация плагина и проверки.

## Содержимое плагина

- `skills/npm-publishing/SKILL.md`: условия применения, полномочия, определение
  текущего состояния, порядок работы, восстановление, критерии завершения.
- `skills/npm-publishing/REFERENCE.md`: команды, npm 2FA, доверие и диагностика
  известных сбоев, ссылки на первичные источники.
- Обычные для репозитория манифесты Claude Code и Codex, записи в обоих каталогах,
  краткий README и обновление каталога в корневом README.
- Проверки манифестов и сценарии поведения в существующем формате репозитория.

Runbook и конфигурация целевого репозитория остаются источником его команд и
релизных правил. Скилл читает актуальные файлы, не дублирует весь runbook и
не фиксирует текущие версии пакетов, номера запусков или идентификаторы доверия.

## Поведение и полномочия

Перед изменениями агент сверяет package.json, release-please, baseline-теги,
проверки CI, точные версии в npm и существующее доверие. Пакет определяется по
имени и пути; репозиторий сверяется с GitHub и package.json. Несовпадение
организации или workflow выявляется до публикации.

Явное поручение подключить пакет разрешает необходимые изменения конфигурации,
PR, push и merge после обязательных проверок, ручную первую публикацию, baseline
Release, настройку или замену ошибочного/истёкшего Publisher этого пакета,
контрольный автоматический выпуск и повтор упавшего publish. Просьба только
проверить или объяснить проблему таких полномочий не даёт. Другие пакеты и
пользовательские изменения вне необходимого объёма не затрагиваются.

Для нового пакета после ручного bootstrap предлагается включить в подключение
контрольный patch-релиз через release-please: одна ручная публикация доверие не
подтверждает. Агент не подменяет этот шаг ещё одной ручной публикацией, не
перезаписывает существующие версии и не придумывает изменения поведения
библиотеки ради повышения версии. Если уже есть неопубликованный выпуск,
использует его вместо создания нового.

## 2FA и восстановление

При запросе npm 2FA агент держит CLI-команду ожидающей, передаёт полную ссылку и
проверяет результат после подтверждения. Не запрашивает у человека токены и
не выводит их. Истёкшее подтверждение возобновляет штатным способом.

После перерыва состояние заново считывается из GitHub и npm. Не публиковать
повторно доступные версии; при частичном выпуске восстановить существующий job.
Учитывать задержку registry, пропущенный publish и различие между повтором
публикации и workflow_dispatch для повторной карточки.

Первую успешную публикацию через новый Publisher выполнить в пределах 48 часов.
Этот срок не трактовать как необходимость периодически продлевать уже
подтверждённое доверие. Истёкшую или неверную конфигурацию пересоздавать с
проверенными repository, workflow, environment и разрешением прямой публикации.

## Приёмка и ограничения

Успех — целевой пакет опубликован workflow через OIDC, точная версия доступна в
registry, dist-tag корректен, публикация и связанные проверки завершились
успешно. Для публичного пакета/репозитория проверяется provenance. Зелёный
workflow с пропущенным publish и один GitHub Release успехом не считаются.

Проверить регистрацию для обоих клиентов и сценарии: новый пакет; повторное
подключение; неверная организация; истёкшее доверие; частичный выпуск; задержка
registry; запрос только диагностики. Проверки поведения использовать на
смоделированных данных, не выпускать реальные версии ради теста скилла.

Новых управляющих скриптов, постоянных npm-секретов, сервиса мониторинга и
поддержки произвольных репозиториев не добавлять. Реализация выбирает точную
структуру коротких разделов и переиспользует существующий формат проверок.
