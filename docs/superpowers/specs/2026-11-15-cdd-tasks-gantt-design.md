# Назначение спринта и дат Gantt через cdd-tasks

Статус: проект спецификации для согласования владельцем.

## Зачем

В Scrumban представление Gantt использует поля `Start Date` и `End Date`.
Назначение только `Sprint` оставляет новую задачу без полосы, а перенесённую —
со старыми датами. Нужна одна воспроизводимая команда агента для назначения
спринта и соответствующих плановых дат.

## Проверенные факты

- В текущем `plugins/cdd-tasks/skills/cdd-tasks/SKILL.md` и `REFERENCE.md`
  назначение следующего спринта меняет только `Sprint` и проверяет сохранение
  `Status`. Это же поведение закреплено в `evals/next-sprint`.
- Исходники находятся в `Cringe-Driven-Development-Team/agent-plugins`;
  установленный экземпляр в кэше Codex не является местом разработки.
- В репозитории уже есть скрипт Python внутри скилла `selectel-ops` и тесты
  через стандартный `unittest`; `cdd-tasks` использует авторизованный `gh`.
- 15 ноября 2026 через полный список карточек GitHub API проверены Scrumban №1,
  поля `Sprint`, `Start Date`, `End Date` и Sprint 9: начало `2026-11-09`,
  длительность 7 дней. Всем 57 задачам Sprint 9 выставлены даты 9–15 ноября,
  повторное чтение подтвердило даты и сохранение статусов и спринтов.
- На скриншоте владельца переключение Gantt с границ Sprint на поля дат оставило
  строки задач без заполненных дат без полос на календаре.
- Официальная документация описывает отдельный выбор источников дат и маркеров:
  <https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/customizing-the-roadmap-layout>.

## Согласованные правила

1. Назначение или перенос задачи в спринт выставляет `Sprint`, `Start Date`
   и `End Date`. Ранее заданный узкий диапазон тоже перезаписывается.
2. По умолчанию начало равно `startDate` итерации, конец —
   `startDate + duration - 1 день`, включительно.
3. Явные даты из текущей просьбы пользователя имеют приоритет над границами
   спринта. Например, «в Sprint 10 на 18–19 ноября» даёт 18–19 ноября;
   просто «в Sprint 10» — 16–22 ноября.
4. Статус и остальные поля не меняются. Разрешение назначить спринт включает
   согласованное заполнение дат; дополнительный вопрос на каждую запись не нужен.
5. Владелец выбрал готовый скрипт вместе с изменением скилла и справочника.

## Рассмотренные подходы

- Только правила и примеры команд: меньше кода, но каждый агент заново собирает
  чтение, вычисление дат, запись и проверку.
- Правила и готовый скрипт: немного поддерживаемого кода и тестов, зато одна
  проверенная операция для повторяющейся работы. Выбран владельцем.

## Предлагаемое устройство

Это небольшое расширение существующего плагина. Следующие технические решения
предложены агентом и входят в согласование этой спецификации.

- Скрипт `plugins/cdd-tasks/skills/cdd-tasks/scripts/set_sprint.py`:
  Python 3, стандартная библиотека и вызовы `gh api graphql` без shell.
  Новых Python-пакетов не требуется.
- Команда принимает одну или несколько явных ссылок на issues организации,
  `--sprint 'Sprint N'`, `--sprint @current` или `--sprint @next`.
  Проект фиксирован: Scrumban №1 организации CDD.
- Необязательные `--start YYYY-MM-DD --end YYYY-MM-DD` задаются парой.
  Без пары используются границы спринта; при частично указанном периоде агент
  уточняет недостающую дату. Скрипт отклоняет неполную пару, несуществующие даты
  и начало позже конца. Явный диапазон не обрезается границами спринта.
- Идентификаторы проекта, полей, итерации и карточек определяются по живым
  данным. Поля дат должны существовать и иметь тип Date; итерация однозначна.
  Полный список карточек читается с пагинацией. Перед первой записью проверяется
  весь набор целей, повторы ссылок устраняются. Отсутствующая или архивированная
  карточка вызывает понятную ошибку; скрипт не добавляет её на доску сам.
- Для относительных спринтов используется сегодняшняя дата `Europe/Moscow`.
  Текущий определяется интервалом `startDate <= today < startDate + duration`,
  следующий — ближайшим началом не раньше конца текущего; порядок массива
  не имеет значения. При перерыве, неоднозначности или отсутствии следующего
  скрипт не угадывает цель и не создаёт итерации; агент уточняет её у владельца.
- Для каждой карточки сохраняются исходные значения, обновляются только три
  целевых поля, затем отдельно перечитываются `Sprint`, обе даты и `Status`.
  Успех выводится только при совпадении с целью и сохранении статуса.
- Запись трёх полей не считается транзакцией. При ошибке, таймауте или
  несовпадении скрипт прекращает дальнейшие записи, пытается прочитать фактические
  значения и сообщает уже обработанные, проблемную и необработанные задачи.
  Если прочитать результат нельзя, явно сообщает неопределённость.
  Автоматического отката и слепого повторения записи нет.

## Документация и проверки

Обновляются `SKILL.md`, `REFERENCE.md`, README плагина, проверка документов
и сценарий `evals/next-sprint`. В скилле добавляются упоминания Gantt и дат для
обнаружения по запросу. Справочник объясняет `Date fields`: начало по `Start Date`,
конец по `End Date`, Sprint отдельно в `Markers`; даты являются плановыми.

Тесты Python без записи в GitHub проверяют расчёт включительного конца, переход
месяца/года, выбор относительных итераций и перерывы, явные и неполные даты,
пагинацию, перезапись старых дат, сохранение статуса, а также частичную ошибку
записи и несовпадение при повторном чтении. Используются подставные ответы `gh`.
Проверяются документация и существующие проверки манифестов.

Пример приёмки: задача с датами 12–13 ноября при переносе в Sprint 10 получает
16–22 ноября; с явными параметрами 18–19 ноября получает 18–19 ноября.
Успешная запись с непроверенным результатом не считается успешным выполнением.

## Границы и дальнейшая работа

Скрипт запускается агентом по поручению владельца. Ручное изменение Sprint
в GitHub само по себе не запускает его. Не добавляются workflow, синхронизация
по расписанию, собственный гант, универсальный клиент Projects, автоматическое
перепланирование зависимостей или массовое изменение задач по неявному фильтру.
При создании задачи без просьбы о спринте даты не назначаются.

После согласования спецификации составляется план. Перед реализацией владелец
выбирает `superpowers:executing-plans` или
`superpowers:subagent-driven-development`, как требуют его постоянные инструкции.
