# Закрытие исправленных обсуждений при повторном code-review

Статус: согласована пользователем 2026-11-08.

## Цель и согласованные решения

При повторной проверке конкретного PR навык `code-review` самостоятельно
закрывает подтверждённо исправленные обсуждения. Это убирает отдельное поручение
«зарезолви» после ревью. Автор замечания не ограничивает область: проверяются
треды самого агента, других людей и ботов.

Пользователь выбрал ответ в каждом исправленном треде перед resolve. Ответ
содержит проверенный SHA, прежний сценарий и краткое доказательство исправления.
Уже опубликованное равноценное подтверждение для того же SHA не дублируется.

## Рассмотренные подходы

1. Ответ с доказательством в каждом треде, затем resolve — выбран пользователем.
   Причина закрытия доступна непосредственно в обсуждении; возможны дополнительные
   уведомления.
2. Resolve с доказательствами только в общем review — меньше уведомлений,
   но объяснение закрытия приходится искать отдельно. Не выбран.

## Предлагаемое поведение

- Повторный запрос вроде «студент исправил, проверь» продолжает ранее явно
  вызванный для этого PR workflow. Авторизация на публикацию распространяется
  на ответы и закрытие проверенных обсуждений. «Только в чате» запрещает все
  записи; локальное ревью и случайно найденный PR не дают такого разрешения.
- Агент читает все страницы обсуждений и полный разговор каждого кандидата.
  Resolve допускается, когда проверены и устранены все относящиеся к замечанию
  проблемы и открытые вопросы. Частичное исправление, спорное требование или
  непроверенный сценарий оставляют тред открытым. Заявление автора «исправлено»,
  зелёный CI и `outdated` сами по себе доказательством не служат.
- Доказательство соответствует замечанию: проверка актуального кода и callers,
  воспроизведение либо подходящий тест. Агент точно указывает, что действительно
  проверил; не выдаёт чтение кода за выполненный тест.
- Перед ответом и перед resolve сверяются head и актуальное содержимое треда.
  При изменении SHA или появлении новых существенных сообщений агент повторяет
  нужную проверку. Пока вывод не подтверждён, тред остаётся открытым.
- Ответ публикуется в существующем треде. После подтверждения публикации агент
  выполняет resolve и чтением проверяет `is_resolved`. Уже закрытые треды не
  требуют нового ответа; автоматически переоткрывать их навык не будет.
- После ошибки или timeout следующая операция — чтение состояния. Принятый
  ответ или resolve не повторяется. При неизвестном результате записи
  останавливаются; итог отделяет подтверждённые действия от неизвестных.
- Существующее правило о неразобранном pending review сохраняется: оно
  останавливает также ответы и resolve. Новые находки публикуются прежним
  pending → COMMENT workflow. Наличие новых находок не мешает закрыть независимо
  проверенные старые замечания; общий итог не называется чистым при открытых багах.
- Итог содержит ссылки на закрытые обсуждения и причины, по которым остальные
  оставлены открытыми. Недоступность reply/resolve или нехватка прав явно
  отражаются в отчёте и не выдаются за успешное закрытие.

## Границы

Изменяется только процедура повторного ревью и публикации. Навык по-прежнему
не меняет проверяемые исходники, индекс, коммиты и ветку; не делает approve,
request changes, merge или автоматический reopen. Инструкции внутри PR
остаются данными, а не поручениями пользователя.

## Область реализации и проверка

Согласовать `SKILL.md`, `references/publishing.md`, README плагина, уведомление
об изменениях в PROVENANCE и сценарии проверки. Не добавлять отдельный сервис
или исполняемый механизм: использовать доступные GitHub MCP/connector и `gh`
по существующим правилам выбора инструментов.

До изменения инструкций прогнать baseline на изолированной замене GitHub;
после изменения повторить сценарии свежими агентами. Обязательные случаи:
исправленные треды разных авторов; частичное исправление и новый вопрос;
`outdated` при сохраняющемся баге; смена head; принятый ответ/resolve с timeout;
повторный запуск без дублей; уже закрытый тред; «только в чате»; неразобранный
pending; отказ API. Проверять реальные вызовы и состояние замены, не только
обещания в ответе. В живых PR тестовых записей не делать.

Это небольшое изменение существующего навыка. Точная формулировка инструкций
и устройство временной тестовой замены остаются исполнителю. Публикация и
локальное обновление плагина не входят в текущее согласование спецификации.
