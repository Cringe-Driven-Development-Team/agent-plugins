# Маркетплейс CDD для Codex Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Подключить четыре плагина CDD к Codex с обнаружением всех 10 существующих навыков и доставкой обновлений без ручных симлинков.

**Architecture:** Каталог `.agents/plugins/marketplace.json` указывает на существующие корни `plugins/<имя>`. Каждый плагин получает `.codex-plugin/plugin.json` с `skills: "./skills/"`; файлы навыков и ресурсов общие для обоих клиентов. Автоматические проверки структуры дополняются приёмкой в реальном Codex и инструкцией в README.

**Tech Stack:** JSON, Bash 3.2, `jq`, Git; Codex CLI 0.162.1 для интеграционной приёмки. Существующие Python unittest используются в регрессионном наборе Selectel.

**Spec:** [2026-10-11-codex-marketplace-design.md](../specs/2026-10-11-codex-marketplace-design.md).

## Global Constraints

- Маркетплейс `cdd`; `interface.displayName: "Cringe Driven Development"`.
- Ровно четыре текущих плагина: `pulumi`, `ansible`, `selectel-ops`, `cdd-tasks`; исходный инвентарь — 6, 2, 1, 1 навыков, всего 10.
- Источник записи: `{"source":"local","path":"./plugins/<имя>"}`; путь разрешается от корня маркетплейса, начинается с `./` и остаётся внутри репозитория.
- Каждая запись содержит `policy.installation: "AVAILABLE"`, `policy.authentication: "ON_INSTALL"`, `category: "Productivity"`.
- Манифест содержит `name`, `description`, `author.name`, `skills: "./skills/"`; имя и автор совпадают с манифестом Claude Code.
- Поле `version` не задаётся в новых манифестах и записях каталога. Несовместимость клиента с этим контрактом требует пересмотра спецификации.
- Сохраняются каталог и манифесты Claude Code, тексты навыков, ресурсы, лицензии и синхронизация апстримов.
- Нет `all-skills`, новых навыков, MCP, приложений, хуков, корневого переносимого `plugin.json` и изменений других репозиториев.
- Автоматические проверки используют `bash` и `jq`; новый менеджер пакетов не нужен.
- Реальная приёмка использует отдельное временное окружение Codex, не меняет личные конфиги, симлинки и установленные плагины пользователя; скрипт Selectel не запускается.

## Review Focus

1. Путь `./../outside`, абсолютный путь или симлинк наружу: проверка отклоняет выход за корень, даже когда там есть корректный `SKILL.md` — задача 1.
2. Отсутствующий или синтаксически неверный JSON и поля неверного типа: проверка завершается ошибкой с именем файла — задача 1.
3. Совпадающее число записей при разных именах, дубликатах или другом авторе: каталоги не считаются согласованными — задача 1.
4. Новый навык в существующем `skills/` и корень репозитория с пробелами: проверка и установка работают без повторного перечисления навыков — задачи 1 и 2.
5. Глобальная копия навыка или старый кэш скрывают ошибку установки: приёмка проверяет источник каждого навыка и содержимое после обновления — задача 2.

Вспомогательные интерфейсы этого тестового файла:

- `make_case(label: string)`: создаёт независимую копию валидной фикстуры; устанавливает `case_root` в абсолютный путь.
- `expect_ok(case_root: path, expected_summary: string)`: вызывает валидатор; проверяет код 0 и указанную строку.
- `expect_fail(case_root: path, diagnostic_fragment: string)`: проверяет ненулевой код и фрагмент пути/имени в диагностике.

Каждый тест вызывает `make_case` и применяет ровно указанную мутацию.

| Тест | Мутация фикстуры | Утверждение в тесте |
|---|---|---|
| `test_valid_inventory` | Нет | `expect_ok "$case_root" 'плагины=4, скиллы=10'` |
| `test_missing_catalog` | Удалить каталог Codex | `expect_fail "$case_root" '.agents/plugins/marketplace.json'` |
| `test_invalid_json` | Повторить отдельно для обоих каталогов и обоих типов манифеста: записать `{` | `expect_fail "$case_root" "$broken_file"` |
| `test_required_fields` | По одному удалить или заменить на `null`/неверный тип обязательное поле каталога, записи или манифеста | `expect_fail "$case_root" "$broken_file"` |
| `test_wrong_values` | Отдельно изменить `name` маркетплейса, `interface.displayName`, `source.source`, обе политики, категорию и `skills`, сохранив корректный тип | `expect_fail "$case_root" "$broken_file"` |
| `test_duplicate_name` | Добавить вторую запись `pulumi` в каталог Codex | `expect_fail "$case_root" 'pulumi'` |
| `test_different_plugin_set` | Сохранив длину массива, заменить `cdd-tasks` на `other` | `expect_fail "$case_root" '.agents/plugins/marketplace.json'` |
| `test_mismatched_identity` | Отдельно изменить имя и автора Codex-манифеста Ansible | `expect_fail "$case_root" 'plugins/ansible/.codex-plugin/plugin.json'` |
| `test_missing_plugin_files` | Отдельно удалить корень плагина, манифест, `skills/` и единственный `SKILL.md` в `cdd-tasks` | `expect_fail "$case_root" 'cdd-tasks'` |
| `test_unsafe_source` | Отдельно задать абсолютный путь, `./../outside`, каталог навыка вместо корня, симлинк на внешний корректный плагин | `expect_fail "$case_root" 'pulumi'` |
| `test_fixed_version` | Отдельно добавить `version: "1.0.0"` в запись каждого каталога и манифест каждого типа | `expect_fail "$case_root" "$broken_file"` |

| `test_root_with_spaces` | Использовать путь временной копии с пробелом | `expect_ok "$case_root" 'плагины=4, скиллы=10'` |

Проверить список изменённых файлов, результаты приёмки и отсутствие правок
общих навыков. Пуш, PR и включение плагинов в личном профиле — отдельные
действия, не входят в выполнение этого плана.

Рекомендуемый способ — subagent-driven: отдельный исполнитель и свежий
ревьюер для каждой задачи, затем ревью всей ветки. Приёмку локального клиента
при необходимости ведёт основной агент, сохраняя те же критерии и отчёт.
До реализации пользователь просматривает план и выбирает способ исполнения.
