# frontend-packages npm-publishing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Добавить в agent-plugins скилл, который доводит существующий пакет frontend-packages от ручного bootstrap до подтверждённой публикации через OIDC.

**Architecture:** Один собственный плагин `frontend-packages`, один скилл `npm-publishing`, отдельный `REFERENCE.md`. Скилл использует актуальный runbook и существующие инструменты целевого репозитория; нового управляющего кода нет. Плагин зарегистрирован для Claude Code и Codex.

**Tech Stack:** Markdown с YAML frontmatter, JSON манифесты, существующие Bash/jq проверки и eval-сценарии; npm и GitHub CLI описаны как инструменты оператора.

**Spec:** `docs/superpowers/specs/2026-11-03-frontend-packages-npm-publishing-design.md` — утверждена пользователем.

## Global Constraints

- Целевой репозиторий: `Cringe-Driven-Development-Team/frontend-packages`; реализация скилла: `Cringe-Driven-Development-Team/agent-plugins`.
- Подключение поручает агенту необходимые публикации, настройку доверия, PR/push/merge и контрольный автоматический выпуск. Человек подтверждает npm 2FA; запрос диагностики остаётся только чтением.
- Использовать существующие команды и runbook; не фиксировать текущие версии, run ID, trust ID и секреты. Не добавлять постоянные npm-токены или управляющие скрипты.
- Новую настройку доверия подтвердить первой успешной публикацией через неё в пределах 48 часов. Не вводить периодического продления подтверждённого Publisher.
- При незавершённом выпуске использовать его, пропуская уже опубликованные версии. Для нового bootstrap провести контрольный patch через release-please, не переписывая версии вручную и не изобретая исправлений поведения библиотеки.
- Успех проверяется по конкретному пакету: OIDC publish, registry, dist-tag, обязательные CI и для публичного выпуска provenance. Пропущенный publish и существующий GitHub Release недостаточны.
- Исполнение плана начинается только после выбора пользователем executing-plans или subagent-driven-development. Не делать настоящих npm/GitHub-публикаций при тестировании скилла.

## Review Focus

1. Пакет уже публиковали вручную, но publish в зелёном workflow пропущен: доверие ещё не подтверждено — `bootstrap`.
2. Один Publisher неверен или истёк, остальные рабочие: исправлять только целевую настройку; имя организации сверять с исходными данными — `trust-recovery`.
3. npm publish успешен, версия ещё не видна: ждать и проверять точную версию, не публиковать поверх неё — `partial-release`.
4. Пользователь просит только проверить сбой: никакой публикации, замены доверия или merge — `diagnostic-only`.
5. 2FA-ссылка неполная/просрочена, CLI всё ещё ожидает: восстановить штатную авторизацию, проверить результат; не объявлять успех по браузеру — `trust-recovery`.
