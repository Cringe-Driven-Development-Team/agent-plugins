# Назначение спринта и дат Gantt: план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Одна команда назначает задачам Scrumban спринт и плановые даты, проверяя сохранённый результат.

**Architecture:** Один скрипт внутри скилла; стандартная библиотека Python и авторизованный `gh api graphql`. Чистые функции рассчитывают цель, CLI проверяет весь список до записи, затем последовательно обновляет и перечитывает карточки. Документация и сценарии скилла используют эту команду.

**Tech Stack:** Python 3.9+ (`zoneinfo`, `argparse`, `datetime`, `json`, `subprocess`, `unittest`), GitHub CLI; bash для существующих проверок. Python 3.9+ — технический минимум из-за `zoneinfo`, новых пакетов нет.

**Spec:** [Согласованная спецификация](../specs/2026-11-15-cdd-tasks-gantt-design.md).

## Global Constraints

- Проект фиксирован: Scrumban №1 организации CDD (`Cringe-Driven-Development-Team`).
- «Назначение или перенос задачи в спринт выставляет `Sprint`, `Start Date` и `End Date`. Ранее заданный узкий диапазон тоже перезаписывается».
- «Явные даты из текущей просьбы пользователя имеют приоритет над границами спринта».
- «Статус и остальные поля не меняются».
- Конец периода включительный: `startDate + duration - 1 день`; сегодня определяется в `Europe/Moscow`.
- `--start` и `--end` принимаются только вместе. Нет создания полей, итераций, карточек, workflow или собственного ганта.
- «Автоматического отката и слепого повторения записи нет». Пакет обновлений не транзакция.
- В тестах нет сети и записи в GitHub. Полноценный запуск скрипта по реальным issues — отдельное поручение владельца, а не проверка реализации.

- До реализации владелец выбирает способ исполнения. Согласование спецификации не является выбором способа.

## Review Focus

1. Карточка на второй странице, дубли ссылок, отсутствующая последняя задача: никаких пропусков и записей до полной проверки (задача 2).
2. Пустой исходный Status и его внешнее изменение во время записи: отсутствие сохраняется; изменение выявляется, без принудительного восстановления (задача 2).
3. Ошибка GraphQL с частичными данными или таймаут после записи: попытка чтения, отчёт о неопределённости, никаких последующих записей (задача 2).
4. Повторные названия спринтов, пересечение итераций, неверная длительность, отсутствие часового пояса: ошибка до мутации, без догадок (задачи 1–2).
5. Ссылка на другой сайт/организацию/PR, некорректный номер и неполная пара дат: ошибка ввода до мутаций, без shell-интерпретации аргументов (задачи 1–2).

### Task 2: Назначить три поля и подтвердить результат через API

**Files:** дополнить тот же `set_sprint.py` и `test_set_sprint.py`.

**Interfaces:**
- Использует функции задачи 1; итерации остаются словарями GitHub.
- `gh_graphql(query: str, variables: dict) -> dict`: возвращает `data`; ошибка CLI,
  сети, JSON или GraphQL вызывает `RuntimeError`, включая случай `data` + `errors`.
- `load_project() -> dict`: проект `{id, fields, items}`, список items полный;
  данные полей содержат id/type и обе группы iterations/completedIterations.
- `read_item(item_id: str) -> dict`: значения `sprint`, `start`, `end`, `status`;
  у Sprint проверяется iterationId, у Status optionId (либо отсутствие), даты ISO.
- `write_schedule(project_id: str, item_id: str, fields: dict, iteration_id: str, start: str, end: str) -> None`:
  обновляет только три поля, не объявляет успех без последующего `read_item`.
- `main(argv=None) -> int`: аргументы — один или несколько URL, обязательный
  `--sprint`, необязательная пара `--start/--end`. Код 0 только при полной проверке,
  2 при неверных аргументах, 1 при ошибке API/данных/проверки. `--help` не вызывает API.
