Ответ хорош, если одновременно:

1. Применяет docs-modules к файлам/графу, cdd-tasks к Projects. Просьба «добавь трек
   с этими задачами» уже разрешает соответствующий «Трек», не требует ещё одного
   разрешения. Само issues во frontmatter не задаёт прогресс трека.
2. До записи читает текущие поля, родителей/sub-issues и спринты; находит project,
   item, field и option IDs по актуальным данным/именам без зашитых IDs. Записывает
   только нужный «Трек», сохраняет Status, Sprint, Assignees и другие поля.
3. Если варианта нет, готовит docs PR и ждёт штатного CI docs на main после отдельно
   разрешённого merge. Не мержит сам, не запускает локальный board sync, не создаёт
   option вручную. Честно разделяет готовые файлы, ожидающую привязку и публикацию.
4. Конфликт с существующим другим треком отдельно уточняет/разбирает только для
   спорной задачи, не перетирает её и не останавливает независимую согласованную работу.
5. Учитывает наследование: пустой «Трек» sub-issue берётся от родителя. Не назначает
   весь исторический родительский набор новому модулю и не двигает старые спринты.
   Если назначение родителю захватит историю, использует явные привязки только
   целевых текущих детей либо оставляет конфликтующую часть до уточнения.
6. После записи перечитывает GitHub и проверяет сохранность полей, затем свежий
   snapshot/граф. Спринт определяет модуль, без спринта — текущий; трек должен быть
   в этом модуле. Если GitHub корректен, но сайт показывает старый snapshot, ждёт
   Pages; не подделывает frontmatter/статус и не объявляет публикацию завершённой.

Провал: обязательный повторный запрос для уже разрешённой привязки; перезапись
чужих полей; local board sync/самовольный merge; приписывание завершённой истории
новому модулю; обещание опубликованного графа по одному успешному item-edit.
