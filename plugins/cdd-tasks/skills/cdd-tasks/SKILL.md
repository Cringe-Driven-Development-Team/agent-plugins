# Задачи и PR команды CDD

Правила команды записаны в `CONTRIBUTING.md` репозитория `Cringe-Driven-Development-Team/.github`.
Этот скилл — как выполнить их командами. Явные инструкции пользователя и уже
согласованные в сессии разрешения имеют приоритет над скиллом. Общекомандные правила
по умолчанию бери из актуального `CONTRIBUTING.md` и workflow владельца; при
расхождении со скиллом сообщи об этом. Личное исключение не делает новую политику
для команды; чтение удалённых правил не отменяет поручение пользователя.

Перед работой прочитай актуальные правила:

```bash
gh api repos/Cringe-Driven-Development-Team/.github/contents/CONTRIBUTING.md -H "Accept: application/vnd.github.raw"
```

Нет доступа — работай по этому скиллу. Точные команды — в `REFERENCE.md` (ссылки «REFERENCE §N»).

## Главное: учебный проект без требования обратной совместимости

У проекта нет живых пользователей; преподаватели проверяют прод примерно раз в месяц.
Между проверками допустимы временная недоступность и несовместимость после выкладки
одной из связанных задач. Не добавляй по своей инициативе в ТЗ, планы, приёмку или PR
требования сохранить старый API/клиент, legacy-режим, поэтапное переключение,
безостановочный деплой или высокий uptime. Такие требования нужны только по прямому
указанию владельца для конкретной задачи. К преподавательской проверке прод должен работать.

Если фронт и бэк можно написать и проверить локально по согласованному целевому контракту,
веди их независимо. Не ставь `Blocked by` только потому, что после мержа одной стороны
прод временно сломается; обозначь точку общей интеграционной проверки после обеих задач.
Не предлагай поддержку двух контрактов как способ обойти такой порядок выкладки.

## Карта: где задача, где код

Задачи заводятся только в `Cringe-Driven-Development-Team`. Обе области перенесены:
код, issues и PR вместе в team/frontend и team/backend.
Учебный `frontend-park-mail-ru/2026_2_Cringe_Driven_Development` — копия main,
Actions там выключены; новых рабочих PR туда не открывать. Проверять текущую
фазу по CONTRIBUTING, а не по наличию исходников в учебной копии.
Учебный `go-park-mail-ru/2026_2_Cringe_Driven_Development` также копия main
без Actions и новых рабочих PR. Ревью остаётся в командных репозиториях.

| Область | Заголовок задачи | Задача — в | Код и PR — в | Ветка | Заголовок PR | Закрывающая строка в PR |
|---|---|---|---|---|---|---|
| фронтенд | `Frontend. …`, `BFF. …` | `Cringe-Driven-Development-Team/frontend` | там же | `web-N` | `WEB-N: <название задачи>` | `Closes #N` |
| бэкенд | `Backend. …` | `Cringe-Driven-Development-Team/backend` | там же | `api-N` | `API-N: <название задачи>` | `Closes #N` |
| инфраструктура | `DevOps. …` | `Cringe-Driven-Development-Team/infra` | там же | по README и последним PR репозитория | так же | `Closes #N` |
| остальное | префикс — в `CONTRIBUTING.md` | репозиторий организации, где лежит код | там же | по README и последним PR репозитория | так же | `Closes #N` |

`N` — номер задачи. Префикс называет область, а не исполнителя; исполнитель — в `Assignees`.
По умолчанию рабочий PR frontend требует review ментора Ярослава, backend — Александра;
обязательное review сохраняется после переноса. Исключение по решению владельца:
`YarikMix` может мержить backend PR без Approve, включая свои; PR, зелёные
`lint/test/docker` и разрешение обсуждений обязательны. Других участников и frontend
исключение не затрагивает. Для остальных репозиториев — их rules/README.
Отдельное действующее разрешение владельца на merge/bypass учитывай по REFERENCE §4.

## Завести задачу

1. Репозиторий и префикс заголовка — по карте. Заголовок: `<Область>. <Что сделать>`.
2. Описание — по шаблону из REFERENCE §1. Разделы «Цель», «Что сделать» и «Приёмка» обязательны
   и называются именно так; «Зависимости» и «Не входит» — когда есть что написать.
   Перед публикацией зафиксируй одно решение для каждого поведения, влияющего на результат.
   Не оставляй исполнителю выбор в обязательных пунктах и приёмке: формулировки «можно A
   либо B» и «на усмотрение исполнителя» делают ТЗ неоднозначным. Если решение уже принято
   владельцем, не возвращай в задачу отвергнутый вариант. Если выбор ещё не сделан, опирайся
   на действующий контракт и контекст; когда их недостаточно, согласуй решение с владельцем
   до передачи задачи в работу. Свободу реализации оставляй там, где она не меняет
   проверяемое поведение и критерии приёмки.
3. Создать через `gh issue create` (REFERENCE §2). Исполнителя ставь сразу, если его назвали
   (`--assignee`). После создания проверь `gh issue view <N> -R <repo> --json assignees`:
   успешная команда создания ещё не доказывает, что GitHub сохранил исполнителя.
   Черновик на доске задачей не считается.
4. После создания сверь раздел «Зависимости» с GitHub Relationships: задачи, без которых
   нельзя начать или проверить текущую даже локально, добавь как `Blocked by` (REFERENCE §2).
   Временная несовместимость на проде между выкладками сама по себе не блокировка. Ссылка в
   описании не создаёт связь. PR и задачи, упомянутые для контекста, оставь ссылками;
   `sub-issue` — отдельный тип связи, описанный ниже.
5. Проверь через API фактический список `Blocked by`, а не только текст задачи. При
   согласованном изменении зависимостей обнови и описание, и связи; не удаляй другие
   существующие связи без основания. Ошибку API сообщи человеку, не объявляй связь готовой.
6. На доску задача попадает сама, в `Backlog`. Не попала — REFERENCE §3.
7. Статус и спринт выставляй, только когда об этом попросили (REFERENCE §3).

## Спринты и представления

`next-sprint` / `Next Sprint` — представление того же проекта Scrumban №1 с фильтром
`sprint:@next`. Просьба «поставь на следующий спринт» означает назначить следующую
итерацию поля `Sprint`, сохранив текущий статус, если отдельно не попросили его изменить.
Выбор итерации по датам, фильтры представлений и команды — REFERENCE §3. До назначения
прочитай статус карточки; после проверь через API сохранённые `Sprint.iterationId` и `Status`.

Если привязанная задача не видна на доске, одного `issue.projectItems` недостаточно:
сверь её с полным списком `projectV2.items` со всеми страницами. При расхождении смотри
REFERENCE §3 «Карточка привязана, но не отображается»: перепривязка проекта помогла
в подтверждённом случае, но требует сохранения и восстановления полей карточки.

## Треки и граф модулей

Просьба «добавь этот трек с указанными задачами в граф» разрешает правку файлов
через `docs-modules` и соответствующую привязку полем «Трек» через `cdd-tasks`.
Повторного разрешения на эту привязку не нужно. Прочитай текущие поля задач,
родителей/sub-issues и спринты; сохрани Status, Sprint, Assignees и остальные поля.
Запись `issues` в подзадаче frontmatter сама по себе не задаёт прогресс трека.

Пустой «Трек» sub-issue наследуется от родителя. Не приписывай завершённые работы
прошлых модулей новому треку: при смешанной истории привяжи явно только целевых
текущих детей, а спорную привязку родителя разбери отдельно. Существующий другой
трек не перезаписывай без решения о переносе; независимые согласованные привязки
выполняй. Спринт определяет модуль; не меняй его ради видимости на графе.

Если варианта поля нет, подготовь docs PR и дождись штатного CI docs на main после
отдельно разрешённого merge. Локальный `module-graph board sync` и ручное создание
варианта не нужны. Разрешение на привязку не разрешает merge. После записи
перечитай GitHub, затем проверь свежий снимок/граф; подготовленный PR и запись
поля ещё не доказывают публикацию. Порядок и команды — REFERENCE §3.

## Работа затрагивает несколько репозиториев

Один PR связывается через `Closes` с одной задачей; момент её закрытия зависит от репозитория. Поэтому работа делится:

1. Родитель — в репозитории той области, куда приходится основная работа.
2. На каждый другой репозиторий — отдельная задача в нём, привязанная к родителю как sub-issue
   (REFERENCE §2). Связь — именно sub-issue: ссылка в тексте или «blocked by» её не заменяют.
3. Пункты «Что сделать» и «Приёмки», которые относятся к другому репозиторию, переезжают в
   sub-issue; в родителе остаётся ссылка на неё.
4. Порядок мержа для корректного закрытия родителя записан и в родителе, и в sub-issue.
   Не назначай его ради непрерывной работы прода между выкладками.

Прогресс `1/1 · 100%` у родительской задачи означает, что закрыта одна из одной
подзадач. Он не показывает `Blocked by` или готовность самой родительской задачи:
она может оставаться открытой при 100%. Проверяй её статус отдельно.

Правка в другом репозитории на пару строк sub-issue не требует: PR идёт с `Part of`.

## Что писать в описании PR

| Ситуация | Строка |
|---|---|
| Рабочий frontend/backend PR | `Closes #N` в соответствующем командном репозитории |
| PR и задача в одном репозитории | `Closes #N` |
| PR в другом репозитории закрывает свою sub-issue | `Closes #N` — номер sub-issue, не родителя |
| PR в репозитории родителя | `Closes #N`; вливается последним, закрытие — по lifecycle репозитория |
| PR родителя должен влиться раньше остальных | `Part of <полная ссылка на родителя>`; родителя закрывает ментор руками после всех sub-issues |
| PR делает только часть задачи | `Part of <полная ссылка>` |

Строка работает в описании PR; в описании задачи и в комментарии она ничего не закрывает.
После `gh pr create` проверь привязку (REFERENCE §4). В frontend `Closes` задаёт связь;
штатно закрывает задачу успешный CD, в backend и остальных репозиториях — merge.
Частичный PR с `Part of` не должен преждевременно закрыть задачу.

## После merge

Проверяй этапы, относящиеся к поручению: merge, push/main CI, course-sync, Release,
production и состояние issue — отдельные результаты. Зелёный Check PR не доказывает
ни сборку main, ни актуальность копии, ни выкатку. Команды CI/sync — REFERENCE §6,
frontend Release/CD/recovery — §7.

| Репозиторий / событие | Штатный результат для задачи |
|---|---|
| Frontend, включая BFF: merge | Issue открыта, `Ready for build` |
| Frontend: проверены артефакты и опубликован Release | Issue открыта, `Ready for release` |
| Frontend: Health check успешен и сохранён production success | CD закрывает issue как `completed`, ставит `Done` |
| Backend и остальные: merge закрывающего PR | Issue закрывается, `Done` |

Открытая frontend issue после merge — нормальный этап. Не закрывай её вручную
для исправления sync или ожидания CD. При явном ручном completed до CD сохраняется
`Done`: merge/публикация не возвращают её в Ready. Ручной reopen после merge
защищён от повторов старого события; новый связанный merge начинает новый цикл.
Успешный rollback ставит `Rollback from production`, не переоткрывая issue;
следующий успешный CD возвращает `Done`. Поздние merge/closed не отменяют
подтверждённый результат актуального цикла. `Ready for test` / `In testing` остаются ручными.

Переходы асинхронны. Сбой course-sync восстанавливай отдельно без deploy (§6).
Если production success подтверждён, но обновление задач упало, используй
`reconcile-issues.yml` с исходным Deployment ID (§7). При сбое merge/closed job
повтори именно соответствующий job после проверки текущего состояния, не весь CI/CD.
В отчёте укажи подтверждённые этапы, SHA/ссылки и оставшийся сбой.

## Задача без PR

Макеты, домашние задания, ручная настройка. Оставь под задачей комментарий со ссылкой на
результат и переведи карточку в `In review`. Закрывает ментор направления после проверки по
«Приёмке».

## Чего ты не делаешь

1. Не инициируешь merge только из-за наличия доступа. При поручении на merge и
   действующем разрешении владельца на bypass review (`gh pr merge --admin`)
   выполняй его без повторного запроса апрува/разрешения: проверь актуальный head,
   обязательные checks именно этого head и отсутствие конфликтов, закрепи SHA
   в операции и проверь результат (§4). Без такого разрешения действует политика
   команды, включая персональное backend-исключение `YarikMix`. Не меняй rulesets
   и не обходи красный/незавершённый CI или конфликты. Изменился head — проверь заново.
2. В задачах, которые создал не ты, без просьбы ничего не меняешь: ни статус, ни спринт, ни
   `Assignees`, ни описание. Каждое такое изменение уходит уведомлением в Telegram-чат команды.
   Свою новую задачу в `Ready` и в спринт тоже переводишь только по просьбе.
3. Не закрываешь руками задачу вместо штатного merge/CD; явное поручение на ручное
   закрытие обрабатывай по правилам репозитория, сохраняя reason и проверяя результат.
