# Задачи и PR команды CDD

Правила команды записаны в `CONTRIBUTING.md` репозитория `Cringe-Driven-Development-Team/.github`.
Этот скилл — как выполнить их командами. Если скилл и `CONTRIBUTING.md` расходятся, прав
`CONTRIBUTING.md`: скажи об этом человеку.

Перед работой прочитай актуальные правила:

```bash
gh api repos/Cringe-Driven-Development-Team/.github/contents/CONTRIBUTING.md -H "Accept: application/vnd.github.raw"
```

Нет доступа — работай по этому скиллу. Точные команды — в `REFERENCE.md` (ссылки «REFERENCE §N»).

## Карта: где задача, где код

Задачи заводятся только в `Cringe-Driven-Development-Team`. Обе области перенесены:
код, issues и PR вместе в team/frontend и team/backend.
Учебный `frontend-park-mail-ru/2026_2_Cringe_Driven_Development` — копия main,
Actions там выключены; новых рабочих PR туда не открывать. Проверять текущую
фазу по CONTRIBUTING, а не по наличию исходников в учебной копии.
Учебный `go-park-mail-ru/2026_2_Cringe_Driven_Development` также копия main
без Actions и новых рабочих PR. Ревью остаётся в командных репозиториях.

| Область | Заголовок задачи | Задача — в | Код и PR — в | Ветка | Заголовок PR | Закрывающая строка в PR |
|---|---|---|---|---|---|---|
| фронтенд | `Frontend. …`, `BFF. …` | `Cringe-Driven-Development-Team/frontend` | там же | `web-N` | `WEB-N: <название задачи>` | `Closes #N` |
| бэкенд | `Backend. …` | `Cringe-Driven-Development-Team/backend` | там же | `api-N` | `API-N: <название задачи>` | `Closes #N` |
| инфраструктура | `DevOps. …` | `Cringe-Driven-Development-Team/infra` | там же | по README и последним PR репозитория | так же | `Closes #N` |
| остальное | префикс — в `CONTRIBUTING.md` | репозиторий организации, где лежит код | там же | по README и последним PR репозитория | так же | `Closes #N` |

`N` — номер задачи. Префикс называет область, а не исполнителя; исполнитель — в `Assignees`.
Рабочий PR frontend требует review ментора Ярослава, backend — Александра;
обязательное review сохраняется после переноса. Исключение по решению владельца:
`YarikMix` может мержить backend PR без Approve, включая свои; PR, зелёные
`lint/test/docker` и разрешение обсуждений обязательны. Других участников и frontend
исключение не затрагивает. Для остальных репозиториев — их rules/README.

## Завести задачу

1. Репозиторий и префикс заголовка — по карте. Заголовок: `<Область>. <Что сделать>`.
2. Описание — по шаблону из REFERENCE §1. Разделы «Цель», «Что сделать» и «Приёмка» обязательны
   и называются именно так; «Зависимости» и «Не входит» — когда есть что написать.
3. Создать через `gh issue create` (REFERENCE §2). Исполнителя ставь сразу, если его назвали
   (`--assignee`). После создания проверь `gh issue view <N> -R <repo> --json assignees`:
   успешная команда создания ещё не доказывает, что GitHub сохранил исполнителя.
   Черновик на доске задачей не считается.
4. После создания сверь раздел «Зависимости» с GitHub Relationships: задачи, после которых
   можно начать или завершить текущую, добавь как `Blocked by` (REFERENCE §2). Ссылка в
   описании не создаёт связь. PR и задачи, упомянутые для контекста, оставь ссылками;
   `sub-issue` — отдельный тип связи, описанный ниже.
5. Проверь через API фактический список `Blocked by`, а не только текст задачи. При
   согласованном изменении зависимостей обнови и описание, и связи; не удаляй другие
   существующие связи без основания. Ошибку API сообщи человеку, не объявляй связь готовой.
6. На доску задача попадает сама, в `Backlog`. Не попала — REFERENCE §3.
7. Статус и спринт выставляй, только когда об этом попросили (REFERENCE §3).

## Работа затрагивает несколько репозиториев

Один PR закрывает одну задачу, поэтому задача делится:

1. Родитель — в репозитории той области, куда приходится основная работа.
2. На каждый другой репозиторий — отдельная задача в нём, привязанная к родителю как sub-issue
   (REFERENCE §2). Связь — именно sub-issue: ссылка в тексте или «blocked by» её не заменяют.
3. Пункты «Что сделать» и «Приёмки», которые относятся к другому репозиторию, переезжают в
   sub-issue; в родителе остаётся ссылка на неё.
4. Порядок мержа записан и в родителе, и в sub-issue.

Прогресс `1/1 · 100%` у родительской задачи означает, что закрыта одна из одной
подзадач. Он не показывает `Blocked by` или готовность самой родительской задачи:
она может оставаться открытой при 100%. Проверяй её статус отдельно.

Правка в другом репозитории на пару строк sub-issue не требует: PR идёт с `Part of`.

## Что писать в описании PR

| Ситуация | Строка |
|---|---|
| Рабочий frontend/backend PR | `Closes #N` в соответствующем командном репозитории |
| PR и задача в одном репозитории | `Closes #N` |
| PR в другом репозитории закрывает свою sub-issue | `Closes #N` — номер sub-issue, не родителя |
| PR в репозитории родителя | закрывает родителя и вливается последним |
| PR родителя должен влиться раньше остальных | `Part of <полная ссылка на родителя>`; родителя закрывает ментор руками после всех sub-issues |
| PR делает только часть задачи | `Part of <полная ссылка>` |

Строка работает в описании PR; в описании задачи и в комментарии она ничего не закрывает. После
`gh pr create` проверь привязку (REFERENCE §4).

## После merge

Для frontend/backend проверь push/main CI для merge SHA, результат course-sync и совпадение
текущих main командного и учебного репозиториев (REFERENCE §6). Если main продвинулся,
проверь новый SHA перед выводом об актуальности копии. В отчёте отдельно укажи merge, CI и sync.
Сбой sync не отменяет merge и закрытие задачи; восстанавливай копию без повторного deploy
по REFERENCE §6.

## Задача без PR

Макеты, домашние задания, ручная настройка. Оставь под задачей комментарий со ссылкой на
результат и переведи карточку в `In review`. Закрывает ментор направления после проверки по
«Приёмке».

## Чего ты не делаешь

1. Не вливаешь PR в обход обязательного ревью (`gh pr merge --admin`, bypass правила) — даже если
   права это позволяют. Скажи человеку, что нужен апрув. Единственное явно согласованное
   исключение — backend merge от `YarikMix`: проверь authenticated account, текущий
   персональный approval ruleset и зелёные обязательные checks; используй обычный merge
   без `--admin`. Если CLI блокирует `Review required` при подтверждённом исключении,
   используй стандартный merge API с exact head SHA по REFERENCE, повторно проверив CI.
   Не расширяй bypass на CI/integrity, других пользователей или frontend.
2. В задачах, которые создал не ты, без просьбы ничего не меняешь: ни статус, ни спринт, ни
   `Assignees`, ни описание. Каждое такое изменение уходит уведомлением в Telegram-чат команды.
   Свою новую задачу в `Ready` и в спринт тоже переводишь только по просьбе.
3. Не закрываешь руками задачу, которую закроет мерж PR.
