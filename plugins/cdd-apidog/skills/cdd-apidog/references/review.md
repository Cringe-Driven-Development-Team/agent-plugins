# Ревью Apidog MR команды CDD

Читай вместе с контекстом `cdd-apidog` и официальным `apidog-branch`.
Результат — замечания к выбранным изменениям с доказательствами и границами
проверки. Ревью контракта не доказывает корректность его реализации.

## 1. Установить состав MR

Из URL возьми project/MR/target, затем прочитай актуальный MR через CLI.
Проверь source/target по ответу, выбранные ресурсы, описание и связанную задачу.
Синтаксис сверяй с текущим help. Пример формы команды для CDD:

```bash
apidog merge-request get <MR_ID> --project 1382426 --to <TARGET_BRANCH>
apidog merge-request preview --project 1382426 --from <SOURCE_BRANCH> --to <TARGET_BRANCH>
```

`get` определяет выбранный состав MR; `preview` помогает найти кандидатов.
В CLI 2.2.12 preview — **не авторитетный backend diff и не diff полей**.
`contentCandidates` не заменяет selection MR. Проверяй `partial`, лимит сканирования
и `unsupportedContentFields`; неизвестное поле означает непроверенный тип данных,
а не отсутствие изменений. Если get не раскрывает выбранный состав достаточно
полно, прочитай его доступным разрешённым способом и до этого не заявляй полное ревью.

Составь перечень выбранных endpoint/schema/mock/прочих ресурсов. Сравнение всех
веток может содержать чужие изменения вне MR: не приписывай их этому MR. Связанные
ресурсы вне selection читай как зависимости; отдельно проверь, будет ли выбранное
изменение работоспособно с версиями этих зависимостей в target после слияния.

## 2. Получить обе стороны

Прочитай выбранные ресурсы в source и **текущем** target, включая `$ref`, общие
ответы и security schemes. CLI reads/exports выполняй с явной веткой и нужным
модулем; сопоставляй stable IDs и пути/методы, учитывай переименование и удаления.
Если документация указывает наследование ресурсов из main, учитывай effective
состояние ветки, а не только её локальные overrides.

MCP refresh полезен лишь при подтверждённых проекте/ветке. Название модуля не
подтверждает source MR; опубликованный сайт CDD показывает main. Для подробного
сравнения используй branch-scoped CLI reads/exports или доступный diff клиента.
Сохрани дату получения, source/target и охват; не называй два разновременных
чтения атомарным snapshot. При существенном изменении веток перепроверь выводы.

OpenAPI покрывает HTTP-контракт, но не доказывает проверку mock expectations,
тестов и других native-ресурсов. Для них используй соответствующее чтение CLI
или доступный UI; одинаковый OpenAPI не означает пустой MR. Недоступное явно
пометь. Экспорты сохраняй отдельно от сгенерированных файлов проекта и проверяй
их охват; не сохраняй содержащие credentials настройки в отчёте.

## 3. Проверить изменения

- Сверь методы, пути, параметры, тела, статусы/ошибки, auth, `required`,
  nullability, ограничения и примеры. Проверь разрешимость refs и соответствие
  релевантных примеров схемам с учётом версии OpenAPI/JSON Schema.
- Сверь семантику с актуальной задачей и конкретными потребителями BFF/frontend/Go:
  состояния, порядок операций, сохранение данных и восстановление после повторного
  открытия. Отсутствие API в локально сгенерированном коде не доказывает отсутствие
  контракта; сначала проверь его свежесть. Если нужна проверка реализации, читай
  относящийся код отдельно и обозначай её как отдельную часть проверки.
- По актуальному backend `docs/apidog.md` проверь риск перезаписи ресурса целиком
  и отката чужих изменений target. Там же описаны ограничения удаления через
  sprint и экспорта auth папки: сравни фактический результат контракта, не только
  видимые настройки UI. Эти особенности относятся к текущему workflow CDD.
- Для моков проверь условия выбора и ответы относительно целевого контракта.
  Запуск `mock:check` — отдельная проверка согласованных сценариев нужной ветки,
  не доказательство работы Go и не обязательная запись ради read-only ревью.

Не требуй backward compatibility/legacy для учебного проекта без поручения.
Различай обнаруженный дефект, неоднозначность контракта и предположение:
если требования или данные не позволяют решить, сформулируй точный вопрос.

## 4. Отдать результат и выполнить порученные действия

В начале — конкретные замечания: серьёзность (P1/P2 и т. п.), ресурс/поле,
сценарий и последствия, ссылка или сравнение source/target, предлагаемая правка.
Затем коротко: project/MR, ветки и время чтения, проверенные типы ресурсов,
результаты проверок и то, что не удалось проверить. При неполном охвате не
подменяй «в проверенной части замечаний нет» утверждением «MR корректен».

Approve/merge, изменение контракта и публикация комментариев/Telegram-сообщений
требуют соответствующего поручения; само «проведи ревью» их не включает.
Если поручение уже есть, не запрашивай его повторно. Перед действием перечитай
актуальные MR/ветки и ограничения доступа; при изменившемся составе сначала
обнови ревью. После действия проверь сохранённый результат, для Telegram reply —
точный алерт и привязку ответа. Не обходи запреты ветки сменой credentials.
