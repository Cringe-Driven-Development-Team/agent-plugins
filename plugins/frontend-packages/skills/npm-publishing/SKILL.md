# npm-публикация frontend-packages

Доводи подключение до **успешной публикации целевого пакета через OIDC и появления
точной версии в npm**. Ручная публикация, созданный GitHub Release и зелёный
workflow с пропущенным publish этого не доказывают.

## Поручение и источники

«Подключи пакет X к автопубликации» разрешает необходимые изменения, PR/push/merge
после проверок, ручной bootstrap, baseline Release, настройку доверия и контрольный
выпуск. Всё автоматизируемое делает агент; человек подтверждает npm 2FA. Не
переспрашивай разрешение на каждый уже порученный шаг. Запрос «проверь/объясни»
разрешает только чтение, даже при наличии write-доступа или совета коллеги.

Найди checkout по remote, прочитай актуальные `AGENTS.md`,
`docs/release-runbook.md`, release-please config/manifest и `.github/workflows/release.yml`.
Проверь доверенный origin и CI выбранного SHA. Имя **со scope**, путь, версию и
component бери из файлов, сверяй repository.url с GitHub. Не затрагивай чужие
изменения и посторонние пакеты. Изменения зависимых пакетов от node-workspace
оценивай в diff release PR, не сливай попавшие туда несвязанные выпуски вслепую.

Команды для нужного состояния — в [REFERENCE.md](REFERENCE.md); читай соответствующий
раздел перед операцией. Используй доступный GitHub-плагин, для отсутствующих операций — `gh`.

## Выбери состояние

| Наблюдение | Следующее действие |
| --- | --- |
| Имени ещё нет в npm | Проверки и ручной bootstrap на проверенном main, затем baseline |
| Версия уже в npm, baseline отсутствует | Проверить происхождение версии, восстановить baseline того же SHA |
| Bootstrap есть, OIDC ещё не проверен | Настроить Publisher и провести контрольный patch через release-please |
| Release есть, версия отсутствует, publish упал | Исправить причину и повторить существующий publish, не повышать версию |
| npm publish exit 0, registry ещё E404/0.0.0-stage | Ждать подтверждения registry; не публиковать заново |
| Версия/latest/provenance и publish/CI/notify подтверждены | Сообщить успех; повторное подключение ничего не выпускает |

## Доверие и 2FA

Для каждого пакета отдельно сверяй **точный repository, release.yml, environment
и Allow npm publish**. `createPackage` в JSON npm trust означает право `publish`,
а не только создание нового имени. Поле expiry может отсутствовать в CLI:
не выдумывай статус; читай доступный API/UI или свидетельства публикации.
Правильную подтверждённую настройку сохраняй, неверную/истёкшую заменяй точечно.

Новый Publisher требует первого успешного publish через него **за 48 часов**;
регулярного продления подтверждённого доверия нет. Не откладывай проверку до
неопределённого будущего изменения. Без готового выпуска используй контрольный
patch из справочника, без фиктивного исправления кода и ручной правки версий.

При `EOTP` держи TTY-команду ожидающей, передай полный живой URL, после
подтверждения прочитай её вывод и exit code. Браузерное «Successful» не заменяет
результат CLI. Не запрашивай коды/пароли/токены и не сохраняй auth URL в документах.
Не добавляй npm-секрет в Actions для исправления OIDC.

## Восстановление и завершение

После перерыва перечитай GitHub/npm: не повторяй уже выполненные шаги.
`not-attempted` после ошибки зависимости восстанавливается тем же publish job.
Проверь смысл workflow_dispatch: в текущем release.yml он повторяет только карточку.
Повторяй после исправления причины; одинаковый сбой без новых данных — остановка
повторов с конкретным блокером.

Дождись завершения publish, обязательных CI и notify; сверь registry **по полному
имени и точной версии**, dist-tag и provenance публичного выпуска с workflow/SHA.
Сообщи версию, ссылку на запуск и оставшиеся ограничения. Отдельно назови то,
что не проверял, например чистую установку. Если нужных прав или инструментов нет,
не подменяй проверенный результат обещанием или ещё одной ручной публикацией.
