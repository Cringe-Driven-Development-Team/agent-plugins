# Критерии анализа

Адаптировано с изменениями из code-review, code-simplifier и comment-analyzer
Anthropic под Apache-2.0. Источники и уведомления: [PROVENANCE.md](../../../PROVENANCE.md).

## Баги и правила проекта

Ищи ошибки в изменениях вместе с нужным контекстом: вызывающими функциями,
контрактами, проверками ввода и тестами. Проверяй достижимость, а не только
подозрительное выражение. Пустой список, граничное значение или особое состояние
может быть полноценным воспроизводимым сценарием. Успешный happy-path тест
не опровергает ошибку на другом допустимом входе.

Для каждого замечания установи:

| Поле | Чем подтвердить |
| --- | --- |
| Место и категория | Конкретная строка изменения; баг или нарушение обязательного правила. |
| Сценарий | Реальный caller и допустимый ввод/состояние, достигающие проблемы. |
| Последствие | Неверный результат, исключение, потеря данных или конкретное нарушение. |
| Доказательство | Воспроизведение или проверяемая цепочка рассуждений по коду и контракту. |
| Исправление | Минимальное направление, которое устраняет причину. |

Например, после удаления initial value из `values.reduce(...)` проверь caller,
фильтрующий список: все элементы могут быть исключены, и пустой список вызовет
исключение. Укажи caller, сценарий и восстановление нейтрального значения;
не ограничивайся утверждением «reduce опасен».

Сверяй правило с действующим AGENTS.md/CLAUDE.md и его областью. Сообщение линтера
может подтвердить нарушение; не подменяй его чужим стилем или общей рекомендацией.
Не требуй тестов каждой функции без связи с риском или правилом проекта.
Недостаток информации обозначь ограничением; неподтверждённую гипотезу не включай
в список найденных багов.

## Комментарии

Проверяй новые и изменённые комментарии, а также прежние, достоверность которых
затронул новый код. Правила одинаковы для русского и английского текста, `//`,
многострочных комментариев, JSDoc/TSDoc и docstrings.

| Содержание | Решение |
| --- | --- |
| Неверное описание порядка, результата, аргументов, ошибок или сложности | Сверить с кодом и контрактом, указать расхождение и точное направление исправления. |
| Устаревшая ссылка или пример | Проверить, что ссылка/пример действительно не соответствует текущему коду. |
| Пересказ очевидного выражения, например «увеличиваем count» перед `count += 1` | Предложить удалить как улучшение: объяснить, что полезной информации не теряется. |
| Причина workaround, инвариант, ограничение, неочевидное решение | Сохранить; проверять точность, а не сокращать ради количества строк. |
| Обязательный JSDoc, лицензия, copyright, директива линтера/компилятора | Сохранить назначение и обязательные элементы. Неверный JSDoc исправлять, а не удалять. |
| Существенная причина отсутствует | Предложить объяснение, только если без него решение действительно вводит в заблуждение. |

Не требуй комментарий каждой функции без правила проекта. Не определяй авторство
ИИ по стилю текста. Для полезного короткого объяснения причины замечание не нужно.

## Упрощение

Ищи повторяющиеся условия, ненужные ветки, обёртки и абстракции в проверяемых
изменениях. Сформулируй конкретную пользу и докажи сохранение поведения, контрактов,
ошибок, побочных эффектов и доступности. Внешне одинаковые выражения с побочными
эффектами не всегда можно объединять или вычислять один раз.

Предпочитай соглашения данного проекта. Не переноси Sentry/React, предпочтение
function/arrow, формат логирования и другие соглашения исходников адаптации.
Меньше строк само по себе не делает код яснее; плотная запись, тернарники и потеря
обработки ошибок не являются улучшением. Предложение остаётся в отчёте, не в коде.

## Перед включением в результат

Проверь вывод ещё раз по исходникам. Одной причине соответствует одно замечание,
даже если она затрагивает баг и комментарий одновременно. Отдели обязательное
исправление от улучшения, укажи точную строку, сценарий и практическое последствие.
Если подтверждённых проблем нет — так и сообщи.
